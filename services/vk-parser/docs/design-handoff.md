## 1. Контекст продукта

Внутренний инструмент команды для аналитики сообществ ВКонтакте. Продукт решает три задачи:

1. **Просмотр кеша уже распарсенных сообществ и их постов** — быстрый доступ к ранее собранным данным.
2. **Парсинг новых данных из ВК по требованию** — сбор свежих постов для заданных групп за указанный период.
3. **Поиск сообществ в ВК** — в том числе тех, которых ещё нет в нашей общей базе, чтобы их можно было распарсить и пополнить общий кеш.

Сервис backend-only: отдельного фронтенда в репозитории нет, дизайн создаётся «с нуля» под REST + (планируемый) WebSocket.

### 1.1 Ключевые технические факты (для информированности)

- Backend: Python, Litestar (ASGI), PostgreSQL (Piccolo ORM), Redis, Kafka (для внешнего distributing результатов).
- Работа с VK API: `aiovk`, используются методы `groups.getById`, `wall.get`, `search.getHints`, `utils.resolveScreenName`.
- Аутентификация: JWT Bearer через внешний AuthService; VK-токен привязан к аккаунту пользователя.
- Префикс API: `/api/v1`. OpenAPI-доки: `/api/v1/vk/docs` (Scalar).
- Парсинг идёт синхронно внутри HTTP-запроса (без очередей), типичное время — от нескольких секунд до десятков секунд в зависимости от объёма.

## 2. Пользовательские сценарии (персоны и роли)

В текущей реализации **два режима доступа**: гость и авторизованный пользователь. RBAC/ролей нет — доступ бинарный.

### 2.1 Гость (неавторизованный)

**Что может:**

- Просматривать список сообществ, которые уже есть у нас в БД (кеш), с подстрочным поиском (`?q=`).
- Открывать карточку любого такого сообщества (`GET /groups/{id}` — возвращает метаданные + `posts_count` в кеше).
- Смотреть сохранённые посты за доступный период.
- Строить графики/топы **по уже закешированным данным** — клиент считает агрегаты сам из выдачи `/groups/{id}/posts` (см. §4.7).
- Видеть базовое состояние системы (health).

**Что НЕ может:**

- Запускать свежий парсинг из ВК.
- Искать сообщества в ВК (в том числе те, которых нет в нашей базе) — ни через REST, ни через WS.
- Получать готовые агрегаты периода от сервера (они возвращаются только из эндпоинта парсинга — защищённого).

**Под капотом:** чтение БД, эндпоинты `GET /api/v1/groups`, `GET /api/v1/groups/{group_id}`, `GET /api/v1/groups/{group_id}/posts`, `GET /api/v1/groups/exists` не требуют JWT.

### 2.2 Авторизованный пользователь

Помимо всего, что может гость:

- **Запускает парсинг**: задаёт список ссылок на сообщества и период — получает агрегаты, топы, таймлайны.
- **Ищет сообщества в ВК** — в том числе те, которых ещё нет в нашем кеше.
- **Пополняет общий кеш новыми сообществами** — неявно, через сам факт их парсинга. После успешного парсинга группа и её посты сохраняются в общую БД и становятся видны всем, в том числе гостям. Персональных списков/подписок/«моих групп» у пользователей **нет** — база одна на всех.

**Под капотом:** `POST /api/v1/parse/vk`, `GET /api/v1/search/vk` требуют `Authorization: Bearer <jwt>` + привязанный VK-токен (`VkAuthenticationError` при его отсутствии).

### 2.3 Матрица доступа (для UI-логики)

| Действие                                                | Гость | Авторизован |
| ------------------------------------------------------- | :---: | :---------: |
| Список групп из кеша (substring `?q=`)                  |   ✓   |      ✓      |
| Карточка группы из кеша (`/groups/{id}`)                |   ✓   |      ✓      |
| Посты группы из кеша                                    |   ✓   |      ✓      |
| Bulk-проверка «в базе / новая» (`/groups/exists`)       |   ✓   |      ✓      |
| Health-статус                                           |   ✓   |      ✓      |
| Запустить парсинг (свежие данные + агрегаты)            |   —   |      ✓      |
| Поиск групп в ВК через REST (`/search/vk`)              |   —   |      ✓      |
| Поиск групп в ВК через WebSocket (`/search/vk/ws`)      |   —   |      ✓      |
| Добавить новую группу в общий кеш (через парсинг)       |   —   |      ✓      |

Для гостевых экранов дизайну желательно явно предусматривать CTA «Войти, чтобы получить свежие данные / найти новые группы».

## 3. Информационная архитектура (предлагаемые экраны)

Эти экраны не заданы бэкендом — это рекомендация, как разложить данные по интерфейсу. Список можно использовать как скелет навигации.

### 3.1 Каталог сообществ (главная)

Источник данных: `GET /api/v1/groups?q=&limit=&offset=`.

- Таблица/грид карточек групп с полями: `photo_url` (аватар), `name`, `screen_name` (@), `members_count`, `last_parsed_at`.
- Пагинация (`limit`/`offset`), подстрочный поиск по query-параметру `q` — ILIKE по `name` **и** `screen_name` одновременно.
- Query-параметр `screen_name` оставлен как exact-match алиас для обратной совместимости (внутренние потребители).
- CTA для авторизованных: «Добавить группу» → открывает поиск ВК (см. 3.4).
- Состояние «пусто»: «В базе пока нет сообществ. Войдите, чтобы добавить первое».

### 3.2 Страница сообщества

Источник данных:

- метаданные + количество закешированных постов: `GET /api/v1/groups/{group_id}` → `{id, name, screen_name, members_count, last_parsed_at, photo_url, cover_url, posts_count}`. Отсутствие записи → 404.
- кеш-посты: `GET /api/v1/groups/{group_id}/posts?start_date=&end_date=&limit=&offset=`.
- свежий парсинг + агрегаты: `POST /api/v1/parse/vk` с `links=[«https://vk.com/{screen_name}»]` и заданным периодом.

Компоненты:

- Шапка: обложка (`cover_url`), аватар (`photo_url`), `name`, `@screen_name`, `members_count`, «обновлено: `last_parsed_at`». Поля `photo_url`/`cover_url` могут быть `null` до первого парсинга — показывать placeholder.
- Таймлайн/график постов за период (см. §4 «Визуализация»).
- Блок метрик периода (ER, ViewsRate и т.д. — см. §4.3).
- Секции «Лучшие посты» / «Худшие посты» — карточки со счётчиками.
- Панель параметров: диапазон дат, top_n (по умолчанию 10), переключатели сортировки (см. §4.5).
- Для авторизованных: кнопка «Обновить» → синхронный парсинг (loader 5–30+ сек).
- Для гостей: бейдж «Снимок кеша. Войдите, чтобы запросить свежие данные».

### 3.3 Парсер (для авторизованного)

Источник: `POST /api/v1/parse/vk`.

- Форма ввода: textarea со ссылками (batch), `start_date`/`end_date` (datetime-picker), `top_n`, флаг `parse_all` («не использовать кеш, перекачать заново»), настройки сортировки.
- Результат: мульти-вкладки по доменам/группам — каждая содержит тот же набор, что и страница сообщества (§3.2).
- Счётчик обработанных доменов (в ответе есть `domains_count`).

### 3.4 Поиск сообществ (в т.ч. отсутствующих в БД)

Этот экран — ключевой UX-вызов. Доступны **два пути**:

- `GET /api/v1/search/vk?q=...` — один запрос = одна выдача, сырой ответ VK `search.getHints`. Оставлен как fallback.
- `WS /api/v1/search/vk/ws?token=<JWT>` — целевой канал, стриминг подсказок (см. §5 — уже реализован).

Важное для дизайна:

- Пользователь должен видеть результаты **по мере ввода** (search-as-you-type).
- Для каждого результата — явный маркер `in_db`: «Уже в нашей базе» vs «Новая — можно добавить». Бэкенд возвращает его автоматически для WS; для REST-выдачи клиент либо добавляет bulk-проверку через `GET /groups/exists?ids=...`, либо игнорирует маркер.
- По клику на «Добавить» — инициируется парсинг этой группы (§3.3).
- На клиенте **не нужно** делать агрессивный debounce — сервер сам отменяет предыдущий inflight при новом вводе (§5.2). Минимальная задержка между отправками одного и того же сокета — 300 мс (иначе ответ `{"error": "rate_limit"}`).

### 3.5 Страница входа / профиль

Логин реализуется на стороне внешнего AuthService (JWT-токен привязывается к аккаунту, далее к нему привязан VK-токен).

Для дизайна важно:

- Экран «нет VK-токена»: аккаунт залогинен, но VK-аккаунт не привязан → призыв привязать (без этого парсинг и поиск ВК вернут 401).
- Индикатор привязки: health возвращает `authenticated: true|false`, `has_vk_token: true|false`, `auth_user_id`.

### 3.6 Вспомогательные экраны

- Health / статус сервиса (для админов/отладки).
- Документация API (встроенная Scalar) — ссылка в подвале.

## 4. Возможности визуализации, которые предоставляет API

Весь «жирный» аналитический payload (графики, топы, готовые агрегаты) отдаёт **один эндпоинт — `POST /api/v1/parse/vk`**. Он требует JWT.

Гостевые эндпоинты (`/groups`, `/groups/{id}`, `/groups/{id}/posts`) возвращают сырые поля — агрегаты на их основе клиент считает сам (см. §4.7 — формулы совпадают с теми, что выполняет сервер для авторизованного flow, код-референс: `period_posts_metrics` в `ParseVkDataAction`).

### 4.1 Структура ответа парсинга (на высшем уровне)

```json
{
  "status": "success",
  "domains_count": 2,
  "data": {
    "clubscreen_name_1": { "...": "..." },
    "clubscreen_name_2": { "...": "..." }
  }
}
```

Внутри каждого домена:

```json
{
  "id": 123,
  "name": "Название сообщества",
  "screen_name": "clubname",
  "members_count": 152430,
  "posts_count": 142,
  "top_posts": [ /* top_n лучших постов */ ],
  "down_posts": [ /* top_n худших постов */ ],
  "graph_data": [ /* ряд точек-постов для графиков */ ],
  "period_posts_metrics": { /* агрегаты периода */ }
}
```

### 4.2 Временной ряд для графиков (`graph_data`)

Это **список постов**, отсортированный выбранной стратегией, с «плоскими» счётчиками. Каждая точка:

```json
{
  "date": 1704067200,        // unix timestamp публикации
  "edit_date": null,         // unix timestamp правки или null
  "views": 12430,
  "likes": 812,
  "comments": 45,
  "reposts": 17,
  "text_len": 384            // длина текста в символах
}
```

**Что с этим можно визуализировать:**

- Линейный/столбчатый график «вовлечённость во времени» (likes/comments/reposts по дате).
- График просмотров во времени.
- Scatter `text_len` × `engagement` (есть ли корреляция длины и реакций).
- Heatmap по дням недели / часам (клиент сам агрегирует по `date`).
- Кумулятивные ряды (post-to-date reach) — расчётом на клиенте.

> Важно: **готовой агрегации «по дням»** (`posts_per_day`) сервер не возвращает. Группировка — задача фронтенда по полю `date`.

### 4.3 Агрегаты за период (`period_posts_metrics`)

Возвращается, только если в периоде есть хотя бы один пост; иначе `null`.

```json
{
  "total_likes": 14231,
  "total_views": 983210,
  "total_comments": 812,
  "total_reposts": 432,
  "total_text_len": 102344,
  "avg_likes": 100.219,
  "avg_views": 6924.717,
  "avg_comments": 5.718,
  "avg_reposts": 3.042,
  "avg_text_len": 721.014,
  "period_posts_count": 142,
  "post_rate": 4.733,        // постов в день
  "engagement_rate": 9.823,  // (likes+comments+reposts) / members * 100
  "views_rate": 32773.667,   // просмотров в день
  "daily_engagement_rate": 0.327,
  "talk_rate": 0.533,        // comments / members * 100
  "love_rate": 9.333         // likes / members * 100
}
```

**Как визуализировать:**

- Большие числовые KPI-карточки (ER, ViewsRate, PostRate).
- Радиальные/progress-индикаторы (ER, TalkRate, LoveRate как % от аудитории).
- Сравнение периодов (клиент делает два запроса за разные диапазоны).
- Benchmark между несколькими группами в batch-парсинге (`data` — словарь доменов, можно сразу показать таблицу сравнения).

### 4.4 Топы и антитопы (`top_posts` / `down_posts`)

Массивы длиной до `top_n` (дефолт 10). Формат каждого элемента — идентичен `graph_data`, но с `id` поста.

Идеи для UI:

- Карусель/список карточек «Лучшие посты недели».
- Parallel-лист «Провалы» (для внутренней аналитики — что не взлетело).
- Переключатель критерия топа — меняет `sort_params` и перезапрашивает (см. 4.5).

### 4.5 Настраиваемая сортировка (`sort_params`)

Клиент может комбинировать несколько факторов сортировки. Каждый фактор имеет приоритет и направление:

```json
"sort_params": {
  "date":             { "priority": 1, "reverse": true  },
  "engagement_rate":  { "priority": 2, "reverse": true  },
  "views":            { "priority": 3, "reverse": true  },
  "comments":         { "priority": 0, "reverse": false },
  "reposts":          { "priority": 0, "reverse": false }
}
```

UI-идея: кнопки-чипы «По дате», «По ER», «По просмотрам» — с возможностью перетаскивания для смены приоритетов (advanced-режим).

### 4.6 Чего НЕТ в API (и это важно учитывать)

Если в макете есть, но в API не реализовано — на handoff нужно явно пометить как «out of scope текущей версии»:

- Демография аудитории (пол, возраст, гео). В устаревшем `docs/api.md` пример упоминал `members_info` — в **актуальном** коде такого поля нет.
- Тексты постов/комментариев / треды обсуждений. Только счётчик `comments` и длина текста (`text_len`).
- Превью медиа (фото/видео постов).
- Аналитика по пользователям (авторы постов, комментаторы) — пайплайн только по сообществам.
- Готовые эндпоинты воронок, heatmap, распределений — всё клиент строит сам из `graph_data`.
- Сравнительные таблицы «топ-N групп между собой». Можно собирать в batch-парсинге вручную.

> Аватар/обложка группы (`photo_url`/`cover_url`) — **добавлены**, но значения появляются только после следующего парсинга группы (заполнение из `groups.getById` с полями `photo_200,cover`). Для групп, которые парсились до этого изменения, поля будут `null` — показывать placeholder.

### 4.7 Гостевые агрегаты (клиентская сборка)

Поскольку `period_posts_metrics` возвращается только из `/parse/vk`, гостевой UI считает те же метрики на клиенте из `/groups/{id}/posts`. Формулы (идентичны серверным):

- `total_*`, `avg_*` — суммы и средние по счётчикам.
- `post_rate = posts_count / days`, где `days = (max_date - min_date).days + 1`, минимум 1.
- `engagement_rate = (likes + comments + reposts) / members * 100`.
- `views_rate = total_views / days`.
- `daily_engagement_rate = (engagements / days) / members * 100`.
- `talk_rate = comments / members * 100`, `love_rate = likes / members * 100`.

Если `members_count` отсутствует или 0 — все `*_rate` показываем как «—».

## 5. Поиск сообществ и WebSocket

### 5.1 REST-поиск (fallback)

- `GET /api/v1/search/vk?q=...` — проксирует `search.getHints` VK. Возвращает сырой формат VK: массив `items` плюс `count`. Один запрос = одна точечная выдача.
- Маркер «в базе / новая» на стороне REST клиент собирает сам через `GET /api/v1/groups/exists?ids=<id1>,<id2>,...` — возвращает `{"data": {"<id>": true|false}}`.
- Rate-limit: **30 rpm на IP** (см. §5.4). Поэтому REST-поиск подходит только для fallback, не для live-набора.

### 5.2 WebSocket-поиск (целевое решение, **реализовано**)

Маршрут: `WS /api/v1/search/vk/ws?token=<JWT>`.

**Протокол сообщений (JSON):**

Клиент → сервер:
```json
{ "q": "любой запрос" }
```

Сервер → клиент (успех):
```json
{
  "q": "любой запрос",
  "cached": false,
  "count": 23,
  "items": [
    { "type": "group", "id": 123, "name": "Имя", "screen_name": "slug", "in_db": true,  "db_group_id": 123 },
    { "type": "group", "id": 456, "name": "Имя", "screen_name": "slug", "in_db": false, "db_group_id": null }
  ]
}
```

Сервер → клиент (ошибки): `{"error": "rate_limit"}`, `{"error": "empty_query"}`, `{"error": "vk_error", "detail": "..."}`. При неверном/просроченном JWT — `close(code=4401)`.

**Поведение:**

- Сервер сам делает **server-side debounce**: при новом сообщении inflight-таск отменяется (`asyncio.Task.cancel`) — клиенту можно отправлять на каждое нажатие, без клиентского debounce (но минимум 300 мс между отправками, см. §5.4).
- Результаты кэшируются в Redis по нормализованному `q` (TTL 120 секунд). Повторный запрос тем же пользователем (или другим в этом окне) придёт с `cached: true`.
- Поле `in_db` — bulk-проверка по локальной таблице `groups`: `in_db=true` → группа уже есть в общем кеше, нажатие на неё ведёт в §3.2 без нового парсинга. `in_db=false` → кнопка «Распарсить», запускает `POST /parse/vk` и пополняет общий кеш.
- При обрыве соединения клиент переподключается. Если сокет нельзя поднять — fallback на §5.1.

**UI-компоненты под это:**

- Combobox с живым списком.
- Скелетоны/shimmer во время ожидания первых результатов.
- Состояние «соединение потеряно» — ненавязчивая плашка + автоматический retry с экспоненциальным бэкоффом.
- Бейдж «✓ в базе» vs «＋ добавить» рядом с каждой подсказкой (по `in_db`).
- Лёгкий индикатор «из кеша» (если `cached: true`) — опционально, для отладки/ощущения «живого» поиска.

### 5.4 Rate-limits (что увидит дизайн)

Пользовательский UX должен учитывать следующие серверные ограничения (in-memory, на IP, per-replica):

| Операция                          | Лимит       | Что видит пользователь при превышении       |
| --------------------------------- | ----------- | ------------------------------------------- |
| Любой HTTP-запрос (глобально)     | 60 rpm      | HTTP 429 `{"detail": "Rate limit reached"}` |
| `POST /parse/vk`                  | 10 rpm      | HTTP 429 (то же сообщение)                  |
| `GET /search/vk` (REST)           | 30 rpm      | HTTP 429                                    |
| `WS /search/vk/ws` (одна сессия)  | ≥ 300 мс/msg| `{"error": "rate_limit"}` в канале          |

Исключены из глобального лимита: `/api/v1/health`, `/api/v1/vk/docs`.

Для дизайна это значит: предусмотреть **toast/inline-уведомление** «Слишком часто, попробуй через пару секунд» (не alert-модалку), без блокировки UI и без счётчика оставшихся запросов (сервер его не отдаёт).

### 5.3 Flow добавления новой группы

1. Пользователь ищет (§3.4) → видит подсказку без маркера «в базе».
2. Нажимает «Распарсить» (пополнить общий кеш).
3. Открывается диалог с параметрами парсинга (период, top_n).
4. Клиент вызывает `POST /api/v1/parse/vk` с одной ссылкой.
5. Группа появляется в каталоге (§3.1), её данные сразу видны и гостям.

Служебная сущность: отмечает, за какие интервалы по конкретной группе данные уже лежат в БД. Для UI интересно только косвенно — может подсвечивать «этот диапазон уже спаршен».

## 7. Состояния экранов

Для каждого основного экрана предусмотреть:

- **Loading** — скелетоны и прогресс. Для парсинга явно показывать «Запрашиваем у ВК…» (может быть 5–60 секунд).
- **Empty (guest)** — «В кеше ничего не найдено. Войдите, чтобы запросить свежие данные».
- **Empty (user)** — «По этому сообществу за выбранный период постов нет».
- **Error 401 (нет JWT)** — «Войдите, чтобы продолжить», CTA → логин.
- **Error VK auth** — «Не привязан VK-аккаунт», CTA → привязать.
- **Error rate-limit (наш, 429)** — см. §5.4. Toast «Слишком часто — подожди пару секунд», без блокирующей модалки.
- **Error rate-limit (VK-side)** — VK возвращает error=6, клиент VK-сервиса делает паузу 3 сек и повторяет; пользователю обычно видно увеличенное время ожидания. Дизайн: «ВК ограничивает частоту запросов, ждём…».
- **Error network / 5xx** — общий fallback с reload.
- **WS-канал потерян** — плашка «Соединение потеряно, переподключаемся», автоматический retry с экспонентой; если N попыток не удалось — fallback-ссылка «Открыть поиск в режиме REST».
- **Error «только пользовательские ссылки»** — пайплайн работает только по группам; если пользователь указал ссылку на профиль, результат будет пустым. Нужен явный хинт: «Мы умеем только сообщества, ссылки на профили игнорируются».

## 10. Открытые вопросы к продакту (опционально для макета)

- Нужны ли превью текста поста и медиа-превью в карточках постов? (В API сейчас нет — при «да» потребуется расширение бэка.)
- Нужны ли демографические графики аудитории? (Нет в API — см. §4.6.)
- Нужна ли страница сравнения групп бок-о-бок? (Можно реализовать клиентски на базе batch-парсинга.)
- Нужно ли показывать пользователю оставшийся rate-limit (счётчик «X из 60»)? Сейчас сервер не отдаёт заголовки с лимитом — при «да» это потребует правок бэкенда.
